# 3. P0 缺陷与修法

## D1 — 训练预算不对等

**问题：** E1 用 100 条真实数据，E2–E5 用 300 条合成数据。V1.0 §7 Step 10 只写了一句"建议固定总优化步数"，没有变成硬约束。

**后果：** E1 与 E2–E5 的任何差值都无法归因到"合成 vs 真实"，因为同时也差了 3 倍数据量。E2–E5 之间的对比不受影响，但整个项目最想讲的那句结论（合成数据能否替代真实数据）失去支撑。

**修法：**

1. **固定总优化步数 S**，所有可训练 arm（E1、Real-300、E2–E5）使用相同的 S、相同的 batch size、相同的优化器与学习率调度。E1 因数据少而多跑 epoch，这是允许的。
2. **新增 Real-300 参照组**：从 Train 剩余池抽 300 条真实标注数据微调。它是"等量真实数据上界"，回答"300 条真实数据能到多少 F1、合成数据离它差多远"。风格参考池相应从 6,918 条缩到 6,618 条。

**影响的实验组：** E1、Real-300、E2–E5 全部。

## D2 — 推理阈值不受控

**问题：** GLiNER 用单一概率阈值判断 span 是否为实体（默认 0.5）。微调后分数分布整体偏移。V1.0 §12 的可复现清单里没有这一项。

**后果：** 这是本项目最容易出现的假阳性来源——"合成数据提升了 F1"可能只是阈值效应。

**修法：** 每个 arm（含 E0）在 Dev Selection 上独立搜索同一网格（0.10–0.90，步长 0.05），按 Micro-F1 选最优阈值，报告所选值。评估阶段一律使用该 arm 自己的阈值。

**影响的实验组：** 全部。

## D3 — 信息预算不对齐

**问题：** E4/E5 需要 Dev Feedback 的 gold 标签算类别 Recall，E2/E3 完全不接触这份数据。于是 E2 vs E4 的差值里同时包含"错误感知的贡献"和"多看了 300 条 gold 标注"的贡献。

**后果：** 2×2 因子实验的主效应与交互项都被污染，V1.0 §9 的核心消融表失去意义。

**修法（信息预算对齐）：**

1. E2/E3 也读取同一份 Dev Feedback，但只用于统计**自然类别分布**，作为生成配额。
2. E4/E5 读取同一份数据，用 `w_c = (1 − R̃_c + ε)^α` 加权后作为配额。
3. 四个 arm 看到的数据完全相同，唯一差别是"拿它做了什么"。

这样 D3 与 D4 的差值才能真正解释为加权函数的贡献。

**影响的实验组：** E2、E3、E4、E5。

## D4 — 统计效力未验证

**问题：** 300 条合成数据、3 个随机种子、per-class Recall 由约 359 个 mention 估出（Dev Feedback 300 句 × 1.195）。

**量化后果：** 若某类在 300 句子集中只有 60–150 个 mention，其 Recall 的 95% 置信区间约为 **±6 到 ±10 个点**。而这类方法的典型增益是 1–3 个 F1 点。连锁反应：

- `R̃_c` 本身不稳 → `w_c` 抖动 → E4 每次跑的采样配额都不同；
- 3 个种子估不准 σ，主表上 0.5 点的差异会被误读为"方法有效"。

**修法：**

1. Phase 3 结束后做 pilot（1 种子 × E0/E1/E2），实测种子间标准差与增益量级，再回定合成数据规模（300 / 500 / 1000）与种子数（3 / 5）。
2. 在 Test 上对实体做 **bootstrap 重采样（1000 次）**，报每个 arm 的 Micro-F1 置信区间。成本极低，比多跑几个种子更直接。
3. 类别 Recall 报支持数，`R̃_c` 用平滑后的值并明确写出 ε、α。

**影响的实验组：** 主表全部，尤其 E4/E5 的权重计算。

## D5 — 主效果可能没有施展空间

**问题：** 类别级 Error-Aware 只在三类 Recall 差异明显时有用。若 E0 三类 Recall 差距小于约 5 点，`1 − R̃_c` 近似均匀，E4 ≈ E2，四组生成数据 + 训练全部白做。

**修法（go/no-go 闸门，设在 Phase 2 之后）：**

| 判据 | 决策 |
|---|---|
| 三类 Recall 极差 ≥ 8 点 | 走原方案：类别级 Error-Aware |
| 极差 5–8 点 | 保留类别级，同时把 boundary 定向作为扩展一起实现 |
| 极差 < 5 点 | **把 V1.0 列为"可选扩展"的 Type/Boundary Error 定向生成升级为主线**，否则方法无立论空间 |

# 4. P1 生成阶段的修正

## D6 — 候选池大小对齐

**问题：** E3/E5 是"N 个候选里挑最好的 300 条"，E2 是"头 300 条通过基础检查的"。两者的候选数、接受率、生成成本都不同；更麻烦的是 best-of-N 会让数据朝 LLM 自身偏好收敛。

**修法：** E2 也从 N 个候选中**随机抽 300 条**（不做质量筛），使候选池大小与生成成本对齐，只让"筛选准则"成为四个 arm 之间的变量。每组记录候选数、接受率、token 用量、成本。

## D7 — 生成器自评偏差

**问题：** E3/E5 的 Calibrator 与 Generator 是同一个 LLM。

**修法：** 把检查项分成两层并分开统计：

| 层次 | 检查内容 | 判定方式 |
|---|---|---|
| 机器可判 | JSON 可解析、标签合法、实体串能在句中定位、区间合法、无重叠、无完全重复、未抄袭参考文本、句长与实体密度达标 | 校验器自动 |
| 需人工判 | 类别语义正确、实体无遗漏、边界完整、语体自然、不过度模板化、上下文一致 | 人工抽检 |

语义子集至少一半换模型或纯人工判定。人工抽检规模建议每 arm 60 条，报 Cohen's κ。

## D8 — 泄漏检查

**修法（两次，都在 Phase 4 之前完成）：**

1. 实体种子清单定稿后，与 `pt_bosque` 的 Test gold 实体做字符串比对，报重叠率；超过 1% 就换种子。
2. 计算 Train（含风格参考池）与 Test 之间的 8-gram 重叠，剔除 Train 侧重复句。

# 5. 复查新增项

## N1 — 句长与实体密度（P0 级，本轮最重要新增）

**实测：** 真实数据每句 1.04–1.20 个实体、23.7–24.5 个 token。V1.0 §7 Step 5 的生成约束只写了"控制句子长度分布"，没有数字。

**后果：** 若 LLM 平均每句给 3 个实体、40 个 token，那么"300 条"这个口径下 E2–E5 得到的实体监督量是 E1（100 条 × 1.154 ≈ 115 个实体）的 **8 倍而不是 3 倍**。D1 的口径对齐随之失效。

**修法：**

1. Prompt 里写死：每句 20–30 个词、1–3 个实体、目标均值 1.2。
2. 校验器硬过滤超界样本。
3. 主表附列每组的"实体/句、token/句、实体总数、token 总数"，让读者能自己判断监督量是否可比。

## N2 — 磁盘（P0 级工程约束）

C 盘剩 33.4 GB，18 份 checkpoint 约 20 GB，加缓存与数据快照会写满；跑到 Phase 6 中途写满且难以回滚。**所有输出（checkpoint、合成数据、预测、缓存）一律放 D:**，C 盘只留代码与配置。

## N3 — HF 下载通道

`huggingface.co` 被 DNS 污染不可达，`hf-mirror.com` 可达。统一设置 `HF_ENDPOINT=https://hf-mirror.com` 后再下载 `pt_bosque` 与 `gliner_multi-v2.1`。此项已有确定答案，不再是待决问题。

## N4 — 质量筛选阈值的独立标定集

E3/E5 的"接受 / 修正 / 丢弃"判据有多严是自由参数。若在生产 300 条上边筛边调，等于让 E3/E5 自己挑样本。**修法：阈值只在 Phase 4 的 30–50 条试产样本上定，写入配置文件后冻结，Phase 5 只执行不修改。**

## N5 — Real-100 的类别覆盖下限

V1.0 §5.3 只要求"包含 PER、ORG、LOC"。若抽到的 100 条里 ORG 只有 2 个 mention，E1 会退化成"只学到 PER"。**修法：分层抽样，保证每类 mention ≥ 20**，并在 `real_100.jsonl` 的生成脚本里写死该约束、输出每类计数。

## N6 — E0 错误画像的阈值口径

`R̃_c` 由 E0 预测算出，但 E0 的阈值是在 Dev Selection 上调的。**修法：明确用"调优后的 E0 阈值"在 Dev Feedback 上重跑一遍，再统计 Recall / FP / FN / Type / Boundary**，与最终评估口径保持一致。

## N7 — 零样本污染（写入 limitations）

`gliner_multi-v2.1` 的预训练数据来自大规模远程监督标注语料，无法证明 `pt_bosque` 的 Test 文本未被覆盖。若 E0 在葡语上意外地强，这是第一个要排查的解释。不拦路，但必须在 limitations 中声明，并附上"E0 的 per-class 表现是否异常高于文献基线"的对照。

# 11. 本轮未采纳的想法（留档）

| 想法 | 不采纳原因 |
|---|---|
| 另建 Python 3.11 环境 | gliner 0.2.30 声明支持 transformers<5.23.0，与现状兼容，先做冒烟测试即可 |
| 每类独立阈值 | 3 类 × 网格搜索会引入更多自由度，Dev 只有 872 条，先做统一阈值 |
| 合成 + 真实混合训练 | 属于另一个研究问题，超出本项目范围 |
| 多种子 × 多 LLM 的方差分解 | 成本过高，先用单 LLM + bootstrap CI 处理 |
